**Date:** 2026-05-09
**Scope:** `vimsbot-contracts/src/**` at HEAD on `main`
**Auditor:** Cascade (internal pair-programming pass, not a substitute for an external audit)
**Methodology:** read-through, coverage gap analysis, targeted Foundry fuzz / invariant / reentrancy tests, 369 passing tests including 23 net-new audit-grade tests across 3 files.

## 1. Executive summary

Two real exploitable issues were found and fixed in-session (`H-02` allowlist bypass, `M-01` releaseAll DoS). Both are now pinned by regression tests. The EIP-712 keeper-commit flow, ERC-2981 royalty wiring, and reentrancy guards on payment paths were stress-tested and held up under cross-domain replay, donation, and reentrancy fuzzing.

The headline blocker for production is **coverage**, not vulnerabilities: three of the five **deployed** evolution hooks (`OracleHook`, `RevenueLevelHook`, `TimeOfDayHook`) currently have **0% test coverage**. They should not be considered safe-to-use until tested; recommended next step before any further mainnet promotion.

## 2. Findings

### H-02 (HIGH, FIXED) — Allowlist bypass when `allowlistEndTime == 0`

**File:** `src/AgentCollectionImpl.sol`, function `mintAgent`
**Status:** Fixed in this session, regression-pinned.

**Description.** The public mint path gated on
```solidity
if (allowlistRoot != bytes32(0) && block.timestamp <= allowlistEndTime) revert AllowlistPhaseActive();
```
Because `block.timestamp <= 0` is always false, configuring an indefinite allowlist via `setAllowlistConfig(root, /*endTime*/ 0, …)` left the public mint open immediately.

The allowlist-side termination check uses different semantics:
```solidity
if (allowlistEndTime > 0 && block.timestamp > allowlistEndTime) revert AllowlistEnded();
```
Here `endTime == 0` correctly means "allowlist forever". The two paths disagreed on what `endTime == 0` meant.

**Impact.** Anyone could bypass the allowlist proof and mint at the public price (`mintPrice`, default 0 wei) while a creator believed they were running an allowlist-only sale.

**PoC.** `test_AUDIT_H02_allowlistBypassClosed_endTimeZero` in `test/audit/AgentCollectionImpl.audit.t.sol` (see file for the original PoC; it is now a regression that asserts the bypass is closed).

**Fix.**
```solidity
if (allowlistRoot != bytes32(0)) {
    if (allowlistEndTime == 0 || block.timestamp <= allowlistEndTime) {
        revert AllowlistPhaseActive();
    }
}
```
Public mint side now mirrors the allowlist side.

### M-01 (MEDIUM, FIXED) — `releaseAll()` DoS via reverting payee

**File:** `src/AgentRoyaltySplitter.sol`, function `releaseAll()`
**Status:** Fixed in this session, regression-pinned.

**Description.** The original implementation reverted the entire batch if a single payee’s ETH receive call failed:
```solidity
(bool ok, ) = acct.call{value: payment}("");
if (!ok) revert TransferFailed();
```
Any payee that is a contract with reverting `receive` could block payouts to all the other recipients in `releaseAll()`. Healthy payees still had the per-payee `release(address)` fallback, so funds were not stuck — but the UX-critical batch path was bricked.

**Impact.** Griefable batch payouts. A malicious co-payee (or a benign multisig with a bad upgrade) freezes the convenience function. Affected secondary-royalty distribution flows for Agent collections that opted into multi-recipient splits.

**PoC.** Original PoC kept and inverted into a regression: `test_AUDIT_M01_releaseAllSkipsRevertingPayee` in `test/audit/AgentRoyaltySplitter.audit.t.sol`.

**Fix.** Skip-on-failure with rollback so the bad payee remains pullable:
```solidity
if (!ok) {
    ethReleased[acct] -= payment;
    totalEthReleased  -= payment;
    emit EthReleaseFailed(acct, payment);
    continue;
}
```
A new `EthReleaseFailed` event surfaces the skip on-chain so off-chain monitors notice. The strict per-payee `release(address)` retains its loud `TransferFailed` revert so callers explicitly opting in to single-payee semantics still see errors.

### L-01 — Fee-on-transfer / rebasing ERC20 tokens under-deliver

**File:** `src/AgentRoyaltySplitter.sol`
**Status:** Documented, not fixed (intentional design).

**Description.** `release(IERC20, address)` records `payment` as released on the splitter side, then `safeTransfer`s `payment` to the payee. With a fee-on-transfer token (e.g., 5% deflationary fee), the payee receives `payment − fee`, but the splitter believes it has paid the full amount. Subsequent payees are short by the cumulative fee.

**Impact.** Only triggers if the splitter is intentionally fed FoT tokens, which is outside the canonical USDC/ETH revenue path. No standard supported token in the deployment list (USDC, ETH) is FoT.

**Recommendation.** Document the unsupported-token list in user-facing copy. If FoT compatibility ever becomes a goal, switch to "received-balance" accounting: snapshot `token.balanceOf(this)` before each `safeTransfer`, treat the difference as the actual delivery, and adjust `erc20Released` accordingly.

**Test:** `test_AUDIT_L01_feeOnTransferUnderDelivers`.

### L-02 — Floor-division dust accumulates per inflow

**File:** `src/AgentRoyaltySplitter.sol`, `_pendingPayment`
**Status:** Documented (acceptable).

**Description.** `_pendingPayment` floors `(totalReceived * sharesBps) / BPS_DENOM`. Across many tiny inflows, ≤ (payees − 1) wei rounds down per inflow, accumulating in the splitter as dead balance.

**Impact.** Negligible (single-digit-wei dust per release). Not loss-of-funds: the next inflow’s release picks it up unless the contract sees only sub-wei deltas, which is impossible for ETH and rare for ERC20.

**Recommendation.** Leave as-is; we already cap acceptable dust at `payees − 1` wei in the conservation invariant (`testFuzz_AUDIT_arbitrarySplitConserves`).

### I-01 — Hook callbacks are called with full remaining gas

**File:** `src/AgentCollectionImpl.sol`, `_callBeforeMint` / `_callAfterMint` / `_callBeforeTransfer` / `_callAfterTransfer`
**Status:** Documented; partial mitigation recommended.

**Description.** The host invokes the active hook with no gas cap. A malicious or buggy `afterMint` / `afterTransfer` hook can burn arbitrary gas before bubbling up. Out-of-gas reverts the entire mint/transfer.

This is partially intended: `beforeTransfer`-revert is the canonical soulbound mechanism (see `IAgentEvolutionHook` docstring). Reverts on observe-only callbacks (`afterMint`, `afterTransfer`) however have no design need to be unbounded.

**Impact.**
- For `before*` hooks: documented design (soulbound, cooldowns, rate-limits). Acceptable.
- For `after*` hooks: a buggy creator-installed hook can grief minters / token holders. The hook is set by `collectionCreator` only, so this is creator-on-user. Not a stranger-on-creator vector.
- A malicious creator does not need a fancy gas hook to grief their own users; they could already lock the collection.

**Recommendation.** Optional follow-up: cap `afterMint`/`afterTransfer` callbacks at e.g. 200 000 gas via `try …{gas: 200_000} catch {}` and treat failure as no-op. Aligns with the ERC-721 receiver convention. **Not adopted in this PR** because (a) it changes the documented hook contract, (b) the impl is at 199 bytes of EIP-170 margin and the extra try/catch needs benchmarking. Tracked for follow-up.

**Test:** `test_AUDIT_I01_hookGasGriefingMeasurable` measures the griefing cost; `test_AUDIT_beforeTransferRevertBlocksMove` pins the soulbound semantic.

### I-02 — Mint accepts overpayment with no refund

**File:** `src/AgentCollectionImpl.sol`, `mintAgent` / `mintAgentAllowlist`
**Status:** Documented (intentional).

**Description.** `mintAgent` only checks `msg.value >= mintPrice` and forwards the entire `msg.value` (split between protocol fee and creator). Overpayment is *kept* by the creator, not refunded.

**Impact.** A user who fat-fingers `value` overpays. No funds are lost to the contract; they go to the creator. Canonical NFT mint pattern, also used by Manifold / Nifty Gateway.

**Recommendation.** Either keep the convention (current) or refund `msg.value − mintPrice` to `msg.sender` for parity with Zora-v3-style mints. UX preference, not a bug.

**Test:** `testFuzz_AUDIT_mintAccountingExact` proves accounting is exact regardless of overpayment.

---

### I-03 — `AgentCollectionImpl` runtime size at 199 / 24 576 bytes (EIP-170 margin tight)

**File:** `src/AgentCollectionImpl.sol`
**Status:** Documented; further refactors plan needed.

**Description.** After the H-02 fix the runtime size is 24 377 bytes — only 199 bytes below EIP-170. Any further feature (e.g., the I-01 mitigation above) will require either extracting more logic into linked libraries (we already extracted the renderer and the EIP-712 helpers), shrinking error strings, or accepting that the impl needs to be split into a delegate-dispatcher pattern.

**Recommendation.** Two reasonable next moves:
1. Split the merkle-allowlist + mint-pricing block into `AgentCollectionMint.sol` external library (estimate 1.5–2 KB savings).
2. Replace bespoke reentrancy guard with OpenZeppelin `ReentrancyGuardUpgradeable` (no size delta but unblocks reuse of audited code).
